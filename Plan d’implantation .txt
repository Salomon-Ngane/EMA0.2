	•	EMA0.2 est un prototype fonctionnel qui dispose d'un backtest basique, mais qui est principalement limité à tester les crossovers.

class RejectionReason(Enum):

    NO_CROSS, NO_RETEST, INSUFFICIENT_DATA, ATR_FILTER_FAILED,

9. ARCHITECTURAL DECISION REQUIRED
Ces points restent des hypothèses de ma part, pas des décisions actées — je ne les implémente pas tant qu'ils ne sont pas tranchés.
	1.	Identifiants : UUID (proposé) vs BIGSERIAL pour les clés primaires de signals/backtests/backtest_trades/validation_runs. UUID facilite la génération côté client (STRATEGY/BACKTEST agents) sans round-trip DB, mais est légèrement plus lourd en index.
	2.	Format de configuration : JSONB (proposé) vs colonnes typées séparées pour configuration/metrics. Impacte directement la facilité des requêtes analytiques du §50.
	3.	Algorithme de config_hash : non spécifié par la Technical Spec. Je propose sha256(json.dumps(config, sort_keys=True)), mais c'est une hypothèse — toute autre équipe reproduisant un backtest doit utiliser exactement le même algorithme.
	4.	Outil de migration : SQL brut versionné dans database/migrations/ (proposé, portable) vs Supabase CLI migrations. Impacte QA Agent/CI.
	5.	Champ signals.status (active/expired/invalidated) et signals.configuration : ne font pas partie du minimum §60 de la spec. Je les propose pour la traçabilité, mais ce sont des ajouts de périmètre — à valider explicitement, sinon je les retire et respecte le minimum strict.
	6.	Rôle pending : actuellement représenté par l'absence de ligne dans users. Mon schéma propose role DEFAULT 'pending', ce qui change le comportement (une ligne serait créée dès le premier /start). C'est une décision produit, pas seulement technique — je ne la tranche pas seul.
	7.	Contrainte CHECK sur role : actuellement aucune contrainte. L'ajouter est un changement de comportement (une valeur de rôle inattendue casserait l'insertion au lieu d'être silencieusement acceptée).
	8.	Ambiguïté transverse hors périmètre DB : AGENTS.md §4 liste un "DOC Agent" et un "ARCHITECT Agent" absents du tableau des 7 agents actifs de PROJECT_STATE.md §6. Signalé pour information — n'affecte pas mon implémentation mais mérite clarification côté ARCHITECT/coordination projet.
	9.	Base de test : Docker Postgres local vs projet Supabase dédié aux tests — dépend d'un arbitrage avec QA Agent, hors de mon autorité seule.

2. Problèmes identifiés
2.1 Autorisation
Problème critique
Le mandat BOT identifie explicitement des problèmes d'autorisation hérités d'EMA0.2.
Le principal objectif sera donc de supprimer tout modèle dans lequel une action privilégiée peut être autorisée uniquement sur la base :
	•	d'un username ;
	•	d'une donnée fournie dans un callback ;
	•	d'un état ancien ;
	•	d'une information utilisateur non vérifiée au moment de l'action.
Le config.py EMA0.2 contient notamment un ADMIN_USERNAME et un ADMIN_ID. (GitHub)
Architecture cible
L'identité Telegram réellement associée à l'update doit être résolue puis comparée aux permissions persistées.
Conceptuellement :
Telegram Update
      ↓
Authenticated Telegram User
      ↓
Database user lookup
      ↓
Permission check
      ↓
Authorized action

2.2 Callback Telegram
Un callback Telegram ne doit jamais être considéré comme une preuve d'identité.
Exemple interdit :
callback_data = "allow:username"
puis autoriser l'opération sur cette seule information.
Le callback ne transporte qu'une intention/UI action.
L'identité doit être récupérée depuis le contexte Telegram de l'utilisateur qui déclenche effectivement le callback.

2.3 Username comme identifiant
Les usernames ne sont pas des identifiants persistants adaptés à l'autorisation ou aux relations métier.
La cible utilisera des identifiants stables, notamment :
telegram_user_id
database user id
asset id
signal id
backtest id
selon le contrat des modules concernés.

2.4 Duplication de logique stratégique
Le bot ne devra contenir aucune logique de :

pivot
crossover
retest
SL
TP
RR

SL/TP

	•	niveau absent ;
	•	niveau structurel incorrect ;
	•	direction LONG ;
	•	direction SHORT.

RR
Tester :
RR = reward / risk
et les frontières :
RR < 2.7

RR > 2.7

7.3 Lookahead tests
Test fondamental :
data jusqu'à T
        ↓
signal(T)
puis :
data jusqu'à T + N
        ↓
signal(T)
Le signal déjà confirmé à T ne doit pas être modifié par des informations futures.
Les pivots nécessitant des candles de confirmation feront l'objet de tests spécifiques afin de distinguer :
pivot occurrence
pivot confirmation
signal availability

8. Risques
R1 — Régression stratégique
Probabilité : élevée pendant migration.
Une modification de la stratégie pourrait changer les résultats historiques.
Mitigation : golden datasets.

R2 — Lookahead
Impact : critique.
Une stratégie pouvant accéder indirectement à des informations futures rendrait les résultats de recherche invalides.
Mitigation : tests temporels dédiés.

R3 — Divergence entre STRATEGY et BACKTEST
Le backtester pourrait involontairement recréer une partie de la stratégie.
Mitigation :
Strategy → SignalSetup → Backtest
et tests d'intégration.
Ce principe est explicitement imposé par l'architecture EMA0.3.

R4 — Ambiguïté SL + TP
Une même candle peut toucher les deux.
Sans politique explicite, deux implémentations peuvent produire des résultats différents.
Décision requise.

R5 — Retest ambigu
Une définition imprécise produit des golden tests artificiels.
Décision STRATEGY requise.

R6 — Migration EMA0.2
La migration peut conserver involontairement un comportement historique qui n'est plus conforme à la spécification.
QA devra distinguer :
historical behavior
vs
EMA0.3 specified behavior

R7 — Dépendances inter-agents
QA dépend principalement de :
MARKET
STRATEGY
BACKTEST
DATABASE
mais ne doit pas devenir propriétaire de leurs implémentations.

11. Critères d'acceptation
Le travail QA sera considéré terminé lorsque :
Tests
	•	 unit tests couvrent les composants déterministes ;
	•	 strategy regression est automatisée ;
	•	 backtest regression est automatisée ;
	•	 integration tests couvrent les interfaces critiques ;
	•	 database tests couvrent persistence + unicité + migrations ;
	•	 lookahead tests passent.
Golden datasets
	•	 fixtures déterministes ;
	•	 expected outputs versionnés ;
	•	 résultats reproductibles ;
	•	 toute divergence détectée automatiquement.
CI
	•	 pytest exécuté automatiquement ;
	•	 lint exécuté ;
	•	 type checking exécuté si retenu ;
	•	 coverage mesurée ;
	•	 integration tests exécutés dans le pipeline approprié.
Qualité
	•	 aucune stratégie réimplémentée dans les tests ;
	•	 aucun comportement stratégique modifié par QA ;
	•	 aucune hypothèse non validée présentée comme contrat ;
	•	 chaque régression possède une cause documentée ;
	•	 documentation QA disponible.
Reproductibilité
Deux exécutions identiques avec les mêmes données, paramètres et version de stratégie doivent produire les mêmes résultats.
